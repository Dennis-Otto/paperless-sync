# Docker end-to-end tests

The suite mounts this checkout read-only as a Nextcloud Custom App and connects it to a deterministic local Paperless API mock. Only [the upgrade from the last release](#the-upgrade-from-the-last-release) installs packages instead, that of the release and that of the commit, as its users get them.

`run-all.sh` runs the scenario against the current release of every Nextcloud version from `min-version` to `max-version` in `appinfo/info.xml`, and against the newest of them on [other databases and object storage](#databases-and-object-storage), with [the upgrade from the last release](#the-upgrade-from-the-last-release), side by side, as the CI does; `run.sh` runs it against one version, by default the one that `compose.yaml` pins, or the image in `NEXTCLOUD_IMAGE`, such as `nextcloud:35-apache`. Every week, the CI also runs it against [the coming Nextcloud](#the-coming-nextcloud), and the app against [a real Paperless-ngx](#contract-tests-against-a-real-paperless-ngx) instead of the mock.

Run locally:

```bash
bash tests/e2e/run-all.sh
bash tests/e2e/run.sh
```

Both need Docker 25 or newer, and Python 3.11 or newer as `python3` or `python`, which checks the answers on your machine. They run in Git Bash on Windows too, with Docker Desktop.

The scenario verifies:

- administrator configuration and server-side token handling, in the browser too: saving after Nextcloud asks for the password, and a new Paperless URL, which needs the token again, see [Accessibility](#accessibility)
- the settings delegated to a group with `occ admin-delegation:add`: a member opens the page in the browser, picks a user and a group, tests, saves and starts a dry-run, while Nextcloud refuses them the status API and a direct write of a key of the app, and another user gets 403 on every route of the page
- a Paperless in the local network without `allow_local_remote_servers`: Nextcloud refuses the mock at its address of the network of Compose, the save says how to allow it and the page moves the focus to *Paperless runs in my local network*, and with that setting on, the whole scenario runs
- the connection checklist: *Test connection* with the token of an account that may view the documents but neither the tags nor add documents and view their tasks names those permissions to grant and the document of another owner that the trash leaves out, and saves nothing; a save with that token goes on with the same checklist; without **View** for UI Settings, the lines of the trash and the upload name that permission; with the token of the full account, every check passes, in the browser too, and a refused local address moves the focus to its setting after *Test connection* as after a save
- the setup of the account of the app with the token of a superuser of the mock: the app creates the account with the permissions of the saved modules, saves the settings with its token and answers a checklist in which nothing fails; a second setup answers `409` and changes the user only with `update`; the token of the superuser is in no answer, not in the configuration of the app and in no line of the log
- the getting-started checklist of the new installation, step by step: the connection first, with the setup check that says that the app is not set up yet, then the dry-run after the save, the schedule after the first dry-run, the first run that completes the list, and the schedule last; in the browser, the list hides after the first successful run, comes back on request, leads each step to its place on the page and follows *Disconnect*, connecting again and the schedule as they happen
- dry-run behavior without filesystem mutations, on the settings page and with `occ paperless_sync:run --dry-run`
- *Synchronize now*, which answers `202` with the queued status before the run starts, and the background job that a worker of Nextcloud runs, whose report the status shows; every other run of the scenario goes through `occ paperless_sync:run`, whose exit code agrees with its report, and `occ paperless_sync:status` reads the same status as the page; without Paperless, both exit with 2
- archive export through the Paperless download API, and a full quota of the target user, which stops the exports of a run
- metadata-only moves without downloading the PDF again, with the SHA-256 checksums of Paperless-ngx 3 and, in a mode of the mock, the MD5 checksums of Paperless-ngx 2
- a mirrored file that keeps its file ID through every move and every new content, a share of it that shows the new content, and the version of the previous content that the background job leaves, which a dry-run right before it doesn't hold back
- the preview of the path template, with the variables of the file names of Paperless, such as the owner, the archive serial number, the name of the month and a custom field, which saves nothing, and a dry-run of unsaved settings, which keeps the saved target user
- titles and names that the path template keeps as plain text, such as `$1` or `{{ correspondent }}`, and long names in Chinese, emoji and Cyrillic, which are shortened to the bytes that Nextcloud accepts
- Paperless inbox-tag exclusion and empty-folder pruning
- tags to mirror: a document without one of them stays out of the archive, the name compared without regard to case, and a tag to mirror that Paperless doesn't have stops the run with exit code 2 before a file changes
- the tags of Paperless as tags of Nextcloud, through WebDAV as Files reads them: a dry-run lists the tag that the copy gets and names the tag whose name a user made already, whatever its case, the run gives the copy the tag of its document as one that users can't assign, the tag that the user put on the copy stays, and without the tag in Paperless the copy loses it
- Paperless trash mirroring and guarded permanent deletion, also after a page of Paperless came back incomplete, and no deletion of a document purged from the trash while permanent deletion is off
- the trash bin of Nextcloud, through its WebDAV API as *Deleted files* reads it: a copy that an excluded tag removes, the folders that its removal empties, a copy that permanent deletion deletes and a copy that leaves the archive of the target user for its owner are in the trash bin of the target user, and a file of the inbox of another user after its import is in the trash bin of that user, although the run set up the files of the target user first
- successful and failed Nextcloud inbox imports, with the ID of the new document and with the reason of Paperless in the `.error.txt`, a duplicate and a task that Paperless revoked, in the task shapes of Paperless-ngx 3.x and 2.20, a file that Paperless refuses, which waits in the inbox until it changes, and a video, a program and an archive, which never go to Paperless, stay in the inbox and are named by a run and a dry-run
- the Activity stream of the target user, through the API of the Activity app: no entry for a dry-run, one entry for a run with the link of the file that it wrote, also for the background job without a user session, and one entry for each import that Paperless finished, with the link of the new document, failed, with its reason, or refused
- the notifications, through the API of the Notifications app: one for the target user for each import that failed or was refused, with its reason; after three runs in a row without Paperless one for the administrator, with the error and a link to the settings, which `occ setupchecks` and the status API of the app report as well, the API to administrators alone; and none of the failing mirror after the next successful run
- target-user ownership and access isolation
- per-user ownership: the connection checklist names who gets the documents of each user of Paperless and those without an owner; a run gives `e2e-owner` and `e2e-other`, the user of Nextcloud of the Paperless user `E2E-Other` whatever the case, the documents of their users of Paperless in their own files, which the other users don't get, and removes the copies that the target user had of them; a file of the inbox of `e2e-owner` becomes theirs in Paperless, through the owner of its document, and comes back into their archive
- the documents that Paperless shares: the connection checklist says who also gets documents of whom; a document of `e2e-owner` that the group of the household may view reaches `e2e-other`, who is in the group, at the same path, and leaves their files, into their trash bin, once the permission is gone, as the dry run says first, while the copy of `e2e-owner` stays
- background-job registration, status reporting, and clean application logs
- the webhook of a workflow of Paperless, called from the container of the mock as Paperless calls it: refused with `401` without the secret, before and after its creation, with every such call counted by Nextcloud's brute-force protection and the count ended by the first call with the secret; with it, a new title moves the copy during the call, without a background job, also for the address of the document that Paperless-ngx 2.x sends; a document that Paperless doesn't show changes nothing, and a call without a document answers `400`; with *Mirror the document during the call* off, the document waits for its background job; no call changes the status of the last run, and the settings page shows the last call, never the secret
- the background job as system cron starts it: once synchronization is enabled and the interval since the last run has passed, it runs, and started again at once, it waits
- a document restored from the Paperless trash, whose copy moves back from the deleted folder without a download
- conflicts: with `skip`, a file of the user at the path of a document stays and the run reports it; with `replace`, the document takes its place
- a document that a complete scan leaves out while Paperless still has it, as pages that shift while a run reads them can: the run asks Paperless for it alone, and its copy stays without a missing scan
- a document that vanishes from Paperless without passing through its trash: its copy waits for the grace runs, then moves to the deleted folder, and stays there, as direct deletion is not allowed
- version 9 of the Paperless API in every request, which the mock counts, the version of Paperless in the status, and a Paperless-ngx 2.15 without version 9, whose run says which Paperless the app needs
- a run that can't reach Paperless, near the end, whose error the log of Nextcloud holds without the token, with the arguments of the frames of its trace that PHP replaced, which Nextcloud 36 writes as `*** sensitive parameters replaced ***`
- a Paperless URL changed through Nextcloud's provisioning API, at the very end, which doesn't get the token until the URL that the token was saved with is back
- the run report on the settings page: its heading, only the counts that are not 0, the errors first with translated badges, a filter for each kind, the link to the folder in Files for the target user, and *Copy report*, in English and German
- accessibility of the administration settings and the run report, see [Accessibility](#accessibility)

Optional environment variables:

- `E2E_PORT`: host port for Nextcloud, default `18083`
- `DOCKER_BIN`: Docker CLI path, default `docker`
- `E2E_PROJECT_NAME`: Compose project name, default `paperless_sync_e2e`
- `NEXTCLOUD_IMAGE`: pinned Nextcloud image override
- `E2E_DATABASE`: the database of Nextcloud, `sqlite` by default, `mysql` for MariaDB or `pgsql` for PostgreSQL, see [Databases and object storage](#databases-and-object-storage)
- `E2E_OBJECTSTORE`: the primary storage of Nextcloud, `local` by default, or `s3` for an object store
- `E2E_ACCESSIBILITY=0`: leave out the accessibility check at the end
- `E2E_COVERAGE=1`: measure which lines and branches of `js/*.js` the checks in the browser run, and fail below the floor, see [Coverage of the JavaScript](#coverage-of-the-javascript)
- `E2E_UPGRADE=1`: run [the upgrade from the last release](#the-upgrade-from-the-last-release) instead of the scenario, with the packages in `E2E_RELEASE_PACKAGE` and `E2E_PACKAGE`, which `packages.sh` downloads and builds when they are empty; `E2E_RELEASE_REPOSITORY`, by default `Dennis-Otto/paperless-sync`, names the repository of the release
- `KEEP_E2E=1`: keep containers and the disposable volume after the suite
- `E2E_IGNORE_MAX_VERSION=1`: enable the app with `--force` on a Nextcloud newer than `max-version`, as `canary.sh` does
- `E2E_ARTIFACTS`: a folder for the evidence of a failure and the traces of the checks in the browser, see [When a run fails](#when-a-run-fails), and with `E2E_COVERAGE=1` for the reports of the coverage, also when the run passes

All credentials, users, filenames, document content, and metadata are synthetic. The Paperless mock rejects every token except the explicit `e2e-only-token` fixture, an account that is no superuser, with every permission of a run, and the owner of every document; `e2e-view-only-token`, an account without the permissions for the tags, for adding documents and for their tasks; `e2e-no-ui-settings-token`, an account without **View** for UI Settings; and `e2e-superuser-only-token`, a superuser, which alone may list, create and change users and gives the accounts that it created their tokens, `e2e-token-of-<username>`, for their passwords. It records whether uploads arrived intact. Like Paperless-ngx, it answers each endpoint only with its permission, names the ID and the permissions of the account in `/api/ui_settings/`, and filters the documents by their owner. Like Paperless, it refuses an upload without a `Content-Length` with `No file was submitted.` It plays Paperless-ngx 3.3.0, or 2.20.15 and 2.15.3 after `/control/paperless/<version>`: it serves the versions of the API that each of them serves, by the header `Accept` or its default, refuses the others with `406 Not Acceptable`, names itself in `X-Version` and `X-Api-Version`, and lists tasks in the shapes of their serializers. `/control/tasks/<end>` and `/control/task-of/<file>/<end>` end tasks with `success`, `failure`, `duplicate` or `revoked`, as Paperless-ngx 3.x stores them. After `/control/uploads/unavailable`, it answers every upload with `503`, as a Paperless behind a proxy whose worker is down, until `/control/uploads/available`.

## Every supported version at once

`run-all.sh` starts `run.sh` for every supported version at the same time, each in a Compose project of its own, `paperless_sync_e2e_<version>`, on the port `18080 + <version>`, such as `18113` for Nextcloud 33. Besides, it runs the newest version on PostgreSQL, and on MariaDB with an S3 object store, in the projects `paperless_sync_e2e_<version>_pgsql` and `paperless_sync_e2e_<version>_mysql_s3`, on ports 100 and 200 higher, and the [upgrade from the last release](#the-upgrade-from-the-last-release) on PostgreSQL and MariaDB, in `paperless_sync_e2e_<version>_pgsql_upgrade` and `paperless_sync_e2e_<version>_mysql_upgrade`, on ports 300 and 400 higher. While one downloads its images, another one installs, so that all take little longer than one. Each `run.sh` of a version also downloads the image of Playwright in the background from its start, and the accessibility check at the end waits for it; the variants of a database or a storage leave that check out, as it doesn't depend on them. When all are done, `run-all.sh` prints the log of each, in a group of its own in the CI, with a table of the results, the database, the storage, the app, the commit or the upgrade from the last release, and the Nextcloud release that each ran, and the time of each of its phases: until its containers run, the setup of Nextcloud and the app, the scenarios, and the checks in the browser. A run that gets slower shows there where it spends the time. `run-all.sh` fails if one of the runs failed.

- `E2E_VERSIONS`: the major versions to run instead, such as `"33 35"`; `none` runs only the variants, on `max-version`
- `E2E_VARIANTS`: the variants to run besides, on the newest of the versions, by default `"pgsql mysql+s3 pgsql+upgrade mysql+upgrade"`: each a database, `sqlite`, `mysql` or `pgsql`, with `+s3` for an object store and `+upgrade` for the upgrade from the last release, which runs on the newest version that the release supports as well; `none` runs none
- `E2E_VERSION_TIMEOUT`: the time after which a run that hangs ends as failed, default `15m`, from its own start, so that the 25 minutes of the job in the CI leave room for a run that first waits for a processor, and the logs of all runs are still printed
- `E2E_SHARD`: `1` or `2`, one half of the runs, as each [job of the CI](#in-the-ci) runs one: shard 1 the oldest and the newest version, shard 2 the variants, and each version between the shard with the lighter load, where a version, with its browser checks, counts as five, a variant as three and an upgrade as two, shard 2 when both weigh as much; a shard with nothing to run passes
- `E2E_PLAN=1`: prints the runs that `run-all.sh` would start, and starts none, such as `E2E_PLAN=1 E2E_SHARD=2 bash tests/e2e/run-all.sh`
- `E2E_PARALLEL`: the runs at once, by default the number of processors of the machine; the next run starts when one ends, in the order of the plan, which has the lightest last
- `E2E_MEMORY_FOLDER`: a folder in memory, such as `/dev/shm`, which keeps the files of Nextcloud and the database of SQLite of each run there, on Linux, and empties them at the start and the end of a run; the CI sets it
- `E2E_ARTIFACTS`: a folder that gets a folder for each run that failed, named by its key, with its log, its title and its evidence, see [When a run fails](#when-a-run-fails); the folder of the newest version also gets the [coverage of the JavaScript](#coverage-of-the-javascript) when the run passes

The run on the newest version measures the [coverage of the JavaScript](#coverage-of-the-javascript), whose table follows that of the runs in the summary of the job.

Ctrl-C ends every run, each with the cleanup of `run.sh`, and prints the logs so far. A failed run names the command that runs it again on its own.

`KEEP_E2E=1` keeps the containers of every run. In the CI, the suite leaves its containers running, as the runner is thrown away with them. The suite turns off the password policy's look-up of new passwords at Have I Been Pwned: a request to the internet that the tests don't need and that can fail.

## How the suite stays quick

A run of `run.sh` makes about 200 calls into its containers: it checks about 100 answers, controls the mock about 50 times and runs `occ` about 50 times. When several runs share the cores of one runner, each call counts, so each takes the quickest way:

| Call | How | Time of a call, measured on one machine |
| --- | --- | --- |
| Into a container | `docker exec` by the ID of the container, which `run.sh` finds after each start, instead of `docker compose exec`, which reads the Compose files again on every call | about 470 ms instead of 630 ms |
| A check of an answer | `assert_json.py`, `assert_log.py` and the small scripts of `run.sh` in the Python of your machine, instead of the Python in the container of the mock | about 60 ms instead of 590 ms |
| A control of the mock | `curl` to the mock on a port of `127.0.0.1` that Docker chooses for each run, so that the runs side by side never meet on one | about 55 ms instead of 590 ms |
| `occ` | the compiled code of Nextcloud in files of the container (`opcache.file_cache_only`, without the JIT of the image), which the official images keep for the web server alone, so that a call doesn't compile all of Nextcloud again | about 500 ms instead of 600 ms |

The web server keeps the settings of the image, so the tests still run Nextcloud as an installation does, and PHP still sees a change of a file, such as `config.php`, by its time. The calls that must come from inside the network of Compose, such as the webhook that Paperless calls, still run in the container of the mock.

Some costs had nothing to do with the tests themselves, and the required checks no longer pay them:

- **Health checks.** Each health check starts a process in its container through Docker. A check every two or three seconds, for up to five runs of two or three containers on the four cores of a runner, took a good part of a core for the whole of the run. The Compose files now check every second while a service starts, with `start_interval`, which needs Docker 25 or newer, and once a minute after that. A service that starts is therefore noticed sooner than before. One late answer on a busy runner doesn't mark a service as unhealthy, as that would fail each later `up --wait` of the run: it takes two in a row. `scripts/check-project.sh` fails when a health check checks often for longer than the start, or gives up after one answer.
- **Snapshots in the traces.** A snapshot of the page at each action of a [trace](#when-a-run-fails) takes about a fifth of the time of the checks in the browser: 220 s with them and 180 s without them on one machine, where the pictures of the trace take another 8 s. The first attempt of a job of the CI leaves them out and keeps the rest of the trace, and the second attempt keeps them too.
- **More runs than processors.** A run that shares a processor with another takes longer and saves nothing, so `run-all.sh` starts no more runs at once than the machine has processors, and the lightest wait.
- **The disk.** With SQLite, each commit waits for the disk. In the CI, the folder `data` of Nextcloud, with its database, stays in memory (`E2E_MEMORY_FOLDER`), on a runner that is thrown away after the job. It is a folder of the runner, as a tmpfs of Compose would be empty after each restart of the container.
- **The download of Playwright.** It starts with the run instead of after the start of the containers, so that unpacking the image doesn't compete with the scenarios.

## In the CI

The workflow `.github/workflows/e2e.yml` runs `run-all.sh` in two jobs side by side, each on a runner of its own, and both are required checks of pull requests. Each runs one shard of the runs (`E2E_SHARD`): `nextcloud` the oldest and the newest supported version, *nextcloud on PostgreSQL, MariaDB and S3* the newest version on [the other databases and S3](#databases-and-object-storage) and [the upgrade from the last release](#the-upgrade-from-the-last-release) on PostgreSQL and MariaDB, and each version between goes to the job with the lighter load, where a version, with its browser checks, counts as five, a variant as three and an upgrade as two. Three versions on the four cores of one runner took more than ten minutes, as they slowed each other down, and each new version of Nextcloud would have added about three more; shared, the slower job runs no more than half of the work ([decision 0029](../../docs/decisions/0029-share-the-end-to-end-runs-between-both-required-jobs.md) and [decision 0032](../../docs/decisions/0032-spend-the-runners-of-the-end-to-end-tests-on-the-tests.md), after [decision 0007](../../docs/decisions/0007-end-to-end-tests-on-real-databases-and-storage.md)). Both jobs get the same versions and variants, so they split them the same way, and `scripts/check-project.sh` checks that the two shards start every run once.

In a pull request, `affected.sh` first compares the merge commit with its base. Only a change of the code, the metadata or the assets of the app (`lib/`, `appinfo/`, `templates/`, `js/`, `css/`, `l10n/`, `img/`, `composer.json`), of the end-to-end tests other than their Markdown and the [contract tests](#contract-tests-against-a-real-paperless-ngx), or of the workflow itself can make the tests fail. In `appinfo/info.xml`, a change that only writes other versions into its lines, as the release bot does in `<version>` and in the addresses of the screenshots and their thumbnails, doesn't count, so a release pull request passes at once, while the upstream bot's change of `max-version`, or a line added or removed, runs the tests. Any other pull request passes the check in seconds, and its summary says *E2E skipped: the change cannot affect the app*.

Of the changes that run the tests, those that can behave differently on another database or storage also run [PostgreSQL, and MariaDB with S3](#databases-and-object-storage): the migrations (`lib/Migration/`), the queries of the state (`lib/Service/SyncStateRepository*`), the files in Nextcloud (`lib/Service/NextcloudStorage*`), the uploads to Paperless (`lib/Service/PaperlessApiService.php`), `appinfo/info.xml` as above, the end-to-end tests and their workflow. The upgrade from the last release runs for a change that can break it: the migrations, the settings and the state that a release stored (`lib/Service/ConfigService.php`, `lib/Model/SyncConfig.php`, `lib/Service/SyncStateRepository*`), the secret of the webhook (`lib/Service/WebhookService.php`), what goes into the package (`.nextcloudignore`, `krankerl.toml`, `scripts/check-package.sh`), `appinfo/info.xml` as above, and the end-to-end tests other than the checks in the browser and their workflow; a change of the package alone runs only the upgrade. For any other change of the app, that job runs only the versions between, if there are any, and its summary says *E2E on SQLite with local storage only*. `scripts/check-project.sh` tests these rules with sample paths and changes.

Every push to `main`, a run by hand and every night run both jobs in any case: the images `nextcloud:<version>-apache` move with each point release of Nextcloud, which the nightly run catches before the next pull request. A newer push to a pull request or to `main` cancels the run of the older one; a run by hand and the scheduled runs go to the end.

A job that fails explains itself, as every check does: its summary and, after the checks, the comment of the PR coach on the pull request say what failed, why that matters and how to run it on your machine, from [`.github/checks.project.toml`](../../.github/checks.project.toml), also on a pull request from a fork. The table of the summary names each version, database and storage with its result and the time of each of its phases, and the last lines of the log the command that runs one that failed again on its own.

## When a run fails

A run that fails leaves what it takes to see why, without running it again. Each job of the end-to-end tests in the CI sets `E2E_ARTIFACTS` to a folder, and its cleanup fills a folder of its own there for each run that failed, named by its key, such as `35` or `35-pgsql-upgrade` (`coming` for the canary). The job keeps them for 14 days as its artifact, `e2e-nextcloud`, `e2e-variants` or `e2e-coming`, which `gh run download RUN --name e2e-nextcloud` downloads:

- `run.log` and `title.txt`: the whole output of the run, as its group in the log of the job, and its title
- `nextcloud.log`: the log of Nextcloud, and `apps.txt`, its apps from `occ app:list`
- `containers.txt` and `containers.log`: the state and the whole logs of the containers, with their times
- `browser/`: of each check in the browser that failed, the trace of each of its windows that was still there, `<check>-<window>.trace.zip`, and a screenshot of the whole of each of their pages, `<check>-<window>-<page>.png`
- `coverage/`: on the newest version, the [coverage of the JavaScript](#coverage-of-the-javascript) up to the failure, with that of each page in `v8/`

The password of the tests is masked in `nextcloud.log`, `apps.txt` and the logs of the containers; the traces show it as the browser typed it, which is harmless, since it exists only in the containers of the tests, like the synthetic tokens of the mock.

## Databases and object storage

Few installations of Nextcloud run on SQLite: most keep their tables in MariaDB, MySQL or PostgreSQL, and larger ones keep their files in an object store with the API of S3. The state of the app lives in two tables of its own, which its migrations create, and on an object store Nextcloud reads every file as a stream of no known size, which once made Paperless refuse every upload of the inbox ([#73](https://github.com/Dennis-Otto/paperless-sync/issues/73)). `run.sh` runs the same scenario on them as well:

```bash
E2E_DATABASE=pgsql bash tests/e2e/run.sh
E2E_DATABASE=mysql E2E_OBJECTSTORE=s3 bash tests/e2e/run.sh
```

`compose.pgsql.yaml` (PostgreSQL 17), `compose.mysql.yaml` (MariaDB 11.4, with the settings that Nextcloud asks for) and `compose.s3.yaml` join `compose.yaml`. The databases keep their data in memory, for speed. [SeaweedFS](https://github.com/seaweedfs/seaweedfs) serves the API of S3 and accepts only the key of the tests; Nextcloud creates its bucket and keeps every file there, through the variables `OBJECTSTORE_S3_*` of its image. SeaweedFS has a fixed number of volumes, `-volume.max`, since the image otherwise counts them by the free memory of the host, and `run.sh` fails when they are fewer than the 14 that the log of its filer and the bucket need: on a runner of GitHub, a filer that wrote first took all 7, and every upload of Nextcloud failed with `Error while writing stream to object store` whenever Nextcloud started more than a minute after SeaweedFS. `run.sh` installs Nextcloud on that database and fails if Nextcloud then runs on another database or storage, so that a variant can't pass on SQLite and its disk by mistake. Renovate keeps their images current, each pinned by its digest.

## The upgrade from the last release

Every other run enables the checkout on empty tables, so a migration there never meets a row, and neither does one that moves the data of an installation in use in its `postSchemaChange`, such as the binding of the token to its URL, the lazy settings or the German names of the folders of an installation in use. Every user of the app runs the migrations on the rows of their installation, when they update the app from the App Store, and one that fails there leaves Nextcloud in maintenance mode or disables the app on every server at once. Nor did a run install the package that users get: the signed one of a release, or the one that krankerl builds from the commit with `.nextcloudignore`. `upgrade.sh` installs both packages, on PostgreSQL and on MariaDB, where most installations keep their tables, and runs the migrations that are newer than the last release on the rows of the release; it names them, or says that none is newer, as long as the last release already holds every migration of the commit ([decision 0028](../../docs/decisions/0028-test-the-upgrade-users-run.md)):

```bash
E2E_DATABASE=pgsql E2E_UPGRADE=1 bash tests/e2e/run.sh
E2E_VERSIONS=none E2E_VARIANTS="pgsql+upgrade mysql+upgrade" bash tests/e2e/run-all.sh
```

  <img src="../../docs/images/diagrams/how-the-upgrade-test-runs.svg" alt="How the upgrade test runs: The upgrade test installs the signed package of the last release, which occ integrity:check-app must find intact while a copy with one changed file fails, and uses it as an administrator does, with the token, per-user ownership, the webhook, the copies of two owners, an import, a retry and a file to send. 1. `packages.sh` downloads `paperless_sync.tar.gz` of the latest release on GitHub into a file, never into a pipe, and builds the package of the commit with krankerl, as the release workflow does, or, without krankerl, from the runtime files of `HEAD` that `scripts/check-package.sh` names, the same files. Both take the commit, not the working tree: commit a change before the upgrade can see it. `compose.upgrade.yaml` keeps the checkout out of the folder of the app, and the test unpacks each package into the volume of Nextcloud, as an update does.
2. `occ integrity:check-app` must find the release intact and signed; a copy of it with one changed file must fail the same check, so that its pass proves something.
3. The release is used as an administrator uses it: the token, per-user ownership with a user of Paperless mapped to another user of Nextcloud, the secret of the webhook, and runs of `occ paperless_sync:run` until the tables hold the copies of two owners, an import whose task Paperless hasn't finished, an import that waits to be tried again after Paperless refused its upload with `503`, and a file that waits to be sent from Files. `upgrade_state.php` records every row of every table of the app, its configuration, its credentials, its executed migrations and every file below the base folder of each user with its ID, and the settings page its settings and the state of the webhook.
4. The package of the commit replaces the release. While the commit still has the version of the release, as between two releases, the test gives it the next patch version, as the release bot will: Nextcloud runs the migrations of an app only for a newer version. `occ upgrade` must pass, Nextcloud must leave maintenance mode, `occ app:list` must show that version, and the table `migrations` must hold exactly the migrations of `lib/Migration/` of the package.
5. `assert_upgrade.py` then compares: every row, column, value, credential, migration and file ID of the release must be there with its value, while new columns, tables, values and settings may come; only `installed_version` and `types`, which Nextcloud writes with every update, may change, and what a migration of the commit changes on purpose, which it names in `UPGRADE_CHANGES` of `upgrade.sh`, as `TABLE.COLUMN` or `appconfig.KEY`, with its reason. The next run must reach Paperless with the stored token, download and upload nothing and leave the retry waiting until the same time; the import of the release must end once Paperless finished its task, and the webhook must accept its secret.

The steps against the release speak only what administrators and their scripts use: the settings, `occ paperless_sync:run`, WebDAV and the routes of *Send to Paperless* and of the webhook. A change of one of them must keep its old way working in `upgrade.sh` until the next release, which the test then starts from. A test-only migration that adds a column `NOT NULL` without a default to a table with rows turns the upgrade red on PostgreSQL, while every other run passes; `test_assert_upgrade.py`, which `scripts/check-project.sh` runs, checks that `assert_upgrade.py` finds each loss it looks for. The upgrade runs on the newest version of Nextcloud that both the release and the commit support, as the users of the release have it before they update; with no such version, `run-all.sh` says that no installation could update the app without updating Nextcloud first.

## Coverage of the JavaScript

The scripts of the app, `js/settings.js`, `js/files.js` and `js/flow.js`, have no build and no unit tests of their own: the checks in the browser are their tests. On the newest Nextcloud, `run-all.sh` sets `E2E_COVERAGE=1`, and `browser.mjs` then records with the coverage of V8 in Chromium which functions and blocks of the scripts of the app each page runs, from before the check gets the page and through every document that it loads, until the page, its window or the browser closes. For that, Chromium starts with RenderDocument for crashed frames alone, as it had it before: otherwise it gives each document of a page a frame of its own, the coverage of V8 ends with the frame, and a check that loads its page again, as `settings.mjs` does, would count only its last document. After the five checks, `coverage.mjs` merges the coverage of every page per script, as c8 does, turns it into the coverage of Istanbul with v8-to-istanbul and prints a table of the share of the lines, branches and functions of each script that the checks run, with the lines that no check runs, which the summary of the job shows below the table of the runs.

The run fails when a script runs a smaller share of its lines or of its branches than its floor in `coverage-floor.json`, or doesn't run at all; *The coverage of the JavaScript in the browser falls below its floor:* then names each, and `failure.py` names it as the first error. A floor is the share that the checks reached, less a point, so that a run that takes another way through a page, such as a status that arrives later, stays above it; when the checks pass a floor by more than a point, the table says so, and a pull request that adds a test raises it. Lower a floor only for code that no check in the browser can reach, and say why in the pull request; a new script of `js/` gets its floor in the same pull request, 0 until a run has measured it, as `coverage.test.mjs` fails otherwise. A check that fails stops early and runs less, so after one the run only reports the coverage.

V8 counts a branch for each block of a function that runs, such as the side of an `if` or a `catch`, so a function that no check calls counts in the lines and the functions, but adds no branches. With `E2E_ARTIFACTS`, the folder of the run gets the reports in `coverage/`, also when it passes: `lcov.info`, which an editor or `genhtml` shows line by line, `coverage-final.json` of Istanbul, the table as `summary.md`, and the coverage of each page in `v8/`. The job keeps them for 14 days as its artifact `e2e-coverage`, without `v8/`; a run that fails keeps them in `e2e-nextcloud`. On your machine, on the newest version that `appinfo/info.xml` names as `max-version`:

```bash
NEXTCLOUD_IMAGE=nextcloud:VERSION-apache E2E_COVERAGE=1 E2E_ARTIFACTS=build/e2e-evidence bash tests/e2e/run.sh
```

`scripts/check-project.sh` runs `node --test tests/e2e/coverage.test.mjs`, which tests the table, the floor and LCOV without a browser, and checks that every script of `js/` has a floor, and `browser.test.mjs` checks that each page records its coverage and that the coverage of a page that the check closed counts.

The scenarios `showcase-moved`, `showcase-trashed` and `showcase-restored` of `showcase.py` are those steps, and each run of them is one of *Synchronize now*, in a window that no picture shows. The App Store gets the scans in the inbox, `04-inbox.png`, and the copy in the deleted folder, `05-trash.png`, as frames of those animations.

Each screenshot of the App Store gets a small thumbnail next to it, `screenshots/<name>-small.png`, which the list of the apps in the App Store shows: `thumbnail.mjs` shrinks it to fit 640 × 400 pixels, twice the 200 pixels of height that the list gives it, each pixel the average of those it covers, and `scripts/check-project.sh` tests it with `node --test thumbnail.test.mjs`. `appinfo/info.xml` names both pictures of each screenshot at the tag of the release, and `tests/Unit/AppInfo/ScreenshotsTest.php` checks that each thumbnail is there, with the size of its screenshot shrunk into that box.

The GIFs show a drawn pointer, since a screenshot has none, and share one palette across their frames. Each comes in both themes, `NAME.gif` in the light one and `NAME-dark.gif` in the dark one, from one recording: every frame is taken in the light theme, which the page shows, then in the dark one, by switching the color scheme of the page (`page.emulateMedia`) and the avatars that Nextcloud draws for each theme, and back; a picture in the other theme waits until Chromium has drawn the background of Nextcloud anew. So a story that changes the app, such as the first synchronization, happens only once, and both GIFs show the same steps. A GIF keeps exact white in its palette, as the paper of a document stays white in the dark theme too, and it stays below 1 MB: a scroll changes every pixel of a frame, so `glide` draws it in three steps, and `node --test screenshots.test.mjs`, which `scripts/check-project.sh` runs, checks the size and that each animation is there in both languages and both themes. A caption says what happens in Paperless or in a run; it takes the colors of the theme and sits in the middle of the content of Files, next to its navigation. The image of Playwright has no font for the interface of Nextcloud, so the script installs Inter (`fonts.conf`). `E2E_PORT` (default `18084`), `E2E_PROJECT_NAME` and `KEEP_E2E=1` work as for `run.sh`. Look at every picture before committing it.

### The same pixels on every run

Two runs of the script draw the same pixels, so that a picture changes only when the app looks different. The data of the mock is fixed, and `frozen.mjs` freezes everything else that the server writes anew on each run, in the answers that the browser gets and never in what the server keeps: each moment of a run shows the moment of the story at which the browser first saw it, 10:20 for the first dry-run, 10:21 for the first synchronization and 10:22 for the runs a few days later, the new secret of the webhook shows as an example secret, and every file in Files changed "a few seconds ago". A request of the browser that `frozen.mjs` makes itself goes again when Apache closed its idle connection in that moment (`route.fetch` with `maxRetries`), as a browser sends its own requests again, so that a poll of the status can't end the render with `socket hang up`. Every picture, and every frame of an animation, waits until the page stands still: no part of it scrolling any more, such as to a new report, its images decoded, its transitions at their end, and two pictures in a row the same; and Chromium decodes each image as it draws it and draws each tile whole (`--disable-checker-imaging`, `--disable-partial-raster`), without which it drew the avatar in the header in one of two ways from run to run. After a change of the theme, it draws the right corners of the settings, a part of the page that scrolls, black now and then, in other frames on each run, so a frame of an animation with black corners (`blackCorners` of `frozen.mjs`) changes the theme back and forth and is taken again. An animation takes its frames at fixed steps of what it shows: it waits for the server without frames, and draws a scroll of the page, such as the one to a new report, in three fixed steps. `scripts/check-project.sh` tests the frozen clock with `node --test frozen.test.mjs`.

## The coming Nextcloud

Every Monday, and when started by hand, the workflow also runs the suite against the coming Nextcloud:

```bash
bash tests/e2e/canary.sh
```

The coming Nextcloud is the newest beta or release candidate of the next major version while Nextcloud publishes one, in `https://download.nextcloud.com/server/prereleases/`, and otherwise the daily build of its master branch, `https://download.nextcloud.com/server/daily/latest-master.tar.bz2`. Nextcloud no longer publishes Docker images of betas and release candidates, so the script checks the signature of the package against the release key of Nextcloud, as the official image does, and puts its code into the image of the newest release, `nextcloud:apache`, which keeps its PHP, Apache and start script. The suite enables the app with `--force`, as `max-version` of `appinfo/info.xml` doesn't name that version yet; the upstream bot raises `max-version` once Nextcloud releases the version.

The canary is no required check and blocks nothing. When it fails, it opens the issue *The coming Nextcloud breaks the app* with a link to the run and the [first error](#when-a-run-fails) of the run, adds every further failed run to it with its own, and closes it once the tests pass again. Its artifact `e2e-coming` holds the trace of a check in the browser that failed, which shows the page of the coming Nextcloud as the test saw it.

A failure of the canary is either a change of Nextcloud that breaks the app or one that breaks only a test. `KEEP_E2E=1 bash tests/e2e/canary.sh` keeps the coming Nextcloud running at `E2E_PORT` after the failure, so a script of Playwright in the network of the Compose project, as `run.sh` starts it, can look at the page as the test saw it: its errors in the console, its address and what it shows.

Optional environment variables, besides those of `run.sh`:

- `CANARY_BASE_IMAGE`: the image whose code the coming Nextcloud replaces, default `nextcloud:apache`
- `CANARY_IMAGE`: the local image the script builds, default `paperless-sync-e2e:coming`
- `E2E_ARTIFACTS`: a folder that gets the folder `coming` when the tests fail, as with `run-all.sh`

## Contract tests against a real Paperless-ngx

The mock answers as the app expects Paperless to answer, and so do the answers in the unit tests; twice, both had drifted from Paperless, in the checksums of Paperless-ngx 2.x and in the tasks of 3.x. The contract tests start a real Paperless-ngx instead, the last release of 2.x (2.20) or the current release of 3.x, and check what it answers:

```bash
bash tests/e2e/run-contract.sh 2
bash tests/e2e/run-contract.sh 3
```

`compose.paperless.yaml` adds Paperless and Redis to `compose.yaml`, by the profile `paperless-2` or `paperless-3`, each line in a Compose project and on a port of its own, so that both run side by side. Renovate keeps both images current by their digests, 2.x within 2.x. Paperless reads the text of the PDFs of the tests without OCR and still keeps an archived version of each, as with scanned documents.

`contract.py` runs in the container of the mock, with Python alone, and does what a household does in Paperless, through its REST API with the token of a synthetic administrator: it uploads three PDFs, waits for their tasks, sets their titles, correspondents, document types, a storage path and a custom field of the type select, writes a note on one, puts one into the trash and back, and uploads a PDF that Paperless can't read, the same file twice and a file of a type that it doesn't take. It checks each answer that the app reads, with every request as the app sends it:

- the documents of a run, which carry the fields of `PaperlessApiService::DOCUMENT_FIELDS` and no other, in pages that follow each other, and with their notes and the names of their authors, as a run asks for them while it writes the metadata next to the archive;
- the trash with `deleted_at`, and the lists of tags with the inbox tag, correspondents, document types, storage paths, custom fields with the IDs of their choices, users, and the account with its permissions;
- the tasks of the uploads, in version 9 and, on 3.x, in version 10 of the API: the document of a success, the reason of a failure, a duplicate, which 2.x refuses and 3.x consumes by default, and a task that Paperless doesn't know;
- the checksums of the metadata, which are the MD5 (2.x) or the SHA-256 (3.x) of the original and the archived download ([decision 0009](../../docs/decisions/0009-checksums-of-paperless-2-and-3.md)), and the search for a document by the checksum of its file;
- the versions of the API: 9 on both lines, 10 on 3.x only, 99 refused with HTTP 406;
- the requests of the setup of the account of the app: the filter of a username, which compares without case, a new user that is no superuser with its permissions by their codenames, a second one of the same name, which Paperless refuses, an update with a new password and other permissions, and the token of the user, which stays the one that it had.

Then the app runs against that Paperless in Nextcloud, and at the end sets up its own account with the token of the administrator, whose checklist fails nowhere; the commands for `curl` between the markers `account-snippet` of `README.md` create another account in the container of Nextcloud, whose token passes the checklist too: it exports two documents with the bytes of their archived versions and writes the sidecar of the invoice, with its note, its author and the label of its custom field, moves one to its new title, keeping the ID of its file, follows it into the trash of Paperless and back, and sends a PDF and a broken file from its inbox, which ends as a new document and in the error folder with the reason of Paperless. The status names the version of Paperless, and the log of Nextcloud has no error of the app and never its token.

The answers of Paperless are the fixtures of the unit tests, in `tests/fixtures/paperless-ngx-2/` and `tests/fixtures/paperless-ngx-3/`, which `PaperlessApiServiceTest` reads. Each run compares the shapes of the new answers with them: a field that Paperless added is a note, a field or an answer that is gone, or a field of another type, fails the run. Two recordings of one image of Paperless are the same bytes: the fixtures hold fixed values instead of its times and durations, the IDs of its tasks and choices, the day of the run, the temporary folders in its messages, and the size and checksums of the archived version, and the permissions are sorted (`stable()` in `contract.py`, whose tests in `test_contract.py` also read the fixtures as they stand). So a fixture that changes is a change of Paperless. To record them anew on your machine:

```bash
CONTRACT_RECORD=1 bash tests/e2e/run-contract.sh 3
```

In the CI, the jobs *Paperless-ngx 2.x* and *Paperless-ngx 3.x* of `.github/workflows/e2e.yml` run every Monday with the canary, when started by hand, and in a pull request that changes how the app talks to Paperless: its client (`lib/Service/Paperless*`, `lib/Model/DocumentFingerprint.php`), the mock, the fixtures, the contract tests or the workflow (`affected.sh` with `E2E_QUESTION=contract`). Each keeps the answers of Paperless as an artifact of the run, so new fixtures need no Docker. They are no required checks ([decision 0015](../../docs/decisions/0015-check-the-mock-against-a-real-paperless.md)); when they fail on Monday, they open the issue *The contract tests against Paperless-ngx fail* with the first error of each line that failed, add every further failed run to it with its own, and close it once they pass again. The contract tests also read the paths, reports, settings and status of the app, so a change there can fail them too; the log of the run says which answer differed.

### New fixtures in the pull request that brings them

When Renovate updates the image of Paperless-ngx, or another pull request changes how the app talks to it, the job of each line runs the app against the real Paperless first. If that passes and fixtures differ from the answers, the job keeps them as the artifact `fixes-paperless-ngx-<line>`, with the version of Paperless next to them, and the workflow *Paperless fixtures* (`.github/workflows/paperless-fixtures.yml`) brings them, as data, with `.github/fixture_bot.py` of `main`:

- On a pull request from a branch of this repository, also one of Renovate, it commits them as `test(fixtures): record the answers of Paperless-ngx X.Y.Z`, as the release app. The checks run again on that commit: the unit tests read the new fixtures, and the contract tests compare them. A new shape fails no job here, because the unit tests judge it in that commit.
- On a pull request from a fork, which no bot may push to, it suggests them at their lines, where the diff of the pull request shows them, and a field that is gone or has another type still fails the job as above. `CONTRACT_RECORD=1` records them on your machine.
- A run of the app that fails keeps nothing: it fails with its explanation, and nothing is pushed. Whether the app or the mock follows such an answer is the decision of a person.
- The label `no-bot-fixes` leaves a pull request alone, so a field that is gone or has another type fails the job there as on a fork. The bot changes existing fixtures and adds none, and it takes only JSON at the paths of fixtures from an artifact. If the contract tests of its own commit record other bytes for a fixture that it just wrote, something differs from run to run: the bot stops and says so on the pull request, instead of committing again.

```bash
CONTRACT_FIXES=/tmp/fixes bash tests/e2e/run-contract.sh 3                          # keeps what a job keeps
CONTRACT_FIXES=/tmp/fixes CONTRACT_BOT_COMMITS=1 bash tests/e2e/run-contract.sh 3   # and a new shape fails nothing
```

On Paperless-ngx 2.x, a task that has just failed first reports `<traceback object at 0x…>` as its result and its reason a moment later; the contract tests wait for the reason, as the app does ([issue #161](https://github.com/Dennis-Otto/paperless-sync/issues/161)).

Optional environment variables:

- `CONTRACT_RECORD=1`: write the answers of Paperless into the fixtures instead of comparing them
- `CONTRACT_RECORDINGS`: a folder that keeps the answers of the run
- `CONTRACT_FIXES`: a folder that keeps the fixtures that differ once the app has passed, with the version of Paperless
- `CONTRACT_BOT_COMMITS=1`: a new shape no longer fails the run when fixtures were kept, because the bot commits them
- `E2E_PORT`, `E2E_PROJECT_NAME`, `KEEP_E2E=1`: as for `run.sh`; the port defaults to 18092 for 2.x and 18093 for 3.x
