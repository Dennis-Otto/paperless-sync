# Docker end-to-end tests

The suite mounts this checkout read-only as a Nextcloud Custom App and connects it to a deterministic local Paperless API mock. Only [the upgrade from the last release](#the-upgrade-from-the-last-release) installs packages instead, that of the release and that of the commit, as its users get them.

On request, Nextcloud keeps its tables in MariaDB or PostgreSQL instead of SQLite, and its files in an object store with the API of S3.">

`run-all.sh` runs the scenario against the current release of every Nextcloud version from `min-version` to `max-version` in `appinfo/info.xml`, and against the newest of them on [other databases and object storage](#databases-and-object-storage), with [the upgrade from the last release](#the-upgrade-from-the-last-release), side by side, as the CI does; `run.sh` runs it against one version, by default the one that `compose.yaml` pins, or the image in `NEXTCLOUD_IMAGE`, such as `nextcloud:35-apache`. Every week, the CI also runs it against [the coming Nextcloud](#the-coming-nextcloud), and the app against [a real Paperless-ngx](#contract-tests-against-a-real-paperless-ngx) instead of the mock.

Run locally:

```bash
bash tests/e2e/run-all.sh
bash tests/e2e/run.sh
```

Both run in Git Bash on Windows too, with Docker Desktop.

The scenario verifies:

- administrator configuration and server-side token handling, in the browser too: saving after Nextcloud asks for the password, and a new Paperless URL, which needs the token again, see [Accessibility](#accessibility)
- a Paperless in the local network without `allow_local_remote_servers`: Nextcloud refuses the mock at its address of the network of Compose, the save says how to allow it and the page moves the focus to *Paperless runs in my local network*, and with that setting on, the whole scenario runs
- the connection checklist: *Test connection* with the token of an account that may view the documents but neither the tags nor add documents and view their tasks names those permissions to grant and the document of another owner that the trash leaves out, and saves nothing; a save with that token goes on with the same checklist; without **View** for UI Settings, the lines of the trash and the upload name that permission; with the token of the full account, every check passes, in the browser too, and a refused local address moves the focus to its setting after *Test connection* as after a save
- the setup of the account of the app with the token of a superuser of the mock: the app creates the account with the permissions of the saved modules, saves the settings with its token and answers a checklist in which nothing fails; a second setup answers `409` and changes the user only with `update`; the token of the superuser is in no answer, not in the configuration of the app and in no line of the log
- the getting-started checklist of the new installation, step by step: the connection first, with the setup check that says that the app is not set up yet, then the dry-run after the save, the schedule after the first dry-run, the first run that completes the list, and the schedule last; in the browser, the list hides after the first successful run, comes back on request, leads each step to its place on the page and follows *Disconnect*, connecting again and the schedule as they happen
- dry-run behavior without filesystem mutations, on the settings page and with `occ paperless_sync:run --dry-run`
- *Synchronize now*, which answers `202` with the queued status before the run starts, and the background job that a worker of Nextcloud runs, whose report the status shows; every other run of the scenario goes through `occ paperless_sync:run`, whose exit code agrees with its report, and `occ paperless_sync:status` reads the same status as the page; without Paperless, both exit with 2
- archive export through the Paperless download API, and a full quota of the target user, which stops the exports of a run
- metadata-only moves without downloading the PDF again, with the SHA-256 checksums of Paperless-ngx 3 and, in a mode of the mock, the MD5 checksums of Paperless-ngx 2
- a mirrored file that keeps its file ID through every move and every new content, a share of it that shows the new content, and the version of the previous content that the background job leaves, which a dry-run right before it doesn't hold back
- the preview of the path template, with the variables of the file names of Paperless, such as the owner, the archive serial number, the name of the month and a custom field, which saves nothing, and a dry-run of unsaved settings, which keeps the saved target user
- titles and names that the path template keeps as plain text, such as `$1` or `{{ correspondent }}`, and long names in Chinese, emoji and Cyrillic, which are shortened to the bytes that Nextcloud accepts
- Paperless inbox-tag exclusion and empty-folder pruning
- tags to mirror: a document without one of them stays out of the archive, the name compared without regard to case, and a tag to mirror that Paperless doesn't have stops the run with exit code 2 before a file changes
- the tags of Paperless as tags of Nextcloud, through WebDAV as Files reads them: a dry-run lists the tag that the copy gets and names the tag whose name a user made already, whatever its case, the run gives the copy the tag of its document as one that users can't assign, the tag that the user put on the copy stays, and without the tag in Paperless the copy loses it
- Paperless trash mirroring and guarded permanent deletion, also after a page of Paperless came back incomplete, and no deletion of a document purged from the trash while permanent deletion is off
- the trash bin of Nextcloud, through its WebDAV API as *Deleted files* reads it: a copy that an excluded tag removes, the folders that its removal empties, a copy that permanent deletion deletes and a copy that leaves the archive of the target user for its owner are in the trash bin of the target user, and a file of the inbox of another user after its import is in the trash bin of that user, although the run set up the files of the target user first
- successful and failed Nextcloud inbox imports, with the ID of the new document and with the reason of Paperless in the `.error.txt`, a duplicate and a task that Paperless revoked, in the task shapes of Paperless-ngx 3.x and 2.20, and a file that Paperless refuses, which waits in the inbox until it changes

- version 9 of the Paperless API in every request, which the mock counts, the version of Paperless in the status, and a Paperless-ngx 2.15 without version 9, whose run says which Paperless the app needs
- a run that can't reach Paperless, near the end, whose error the log of Nextcloud holds without the token, with the arguments of the frames of its trace that PHP replaced, which Nextcloud 36 writes as `*** sensitive parameters replaced ***`
- a Paperless URL changed through Nextcloud's provisioning API, at the very end, which doesn't get the token until the URL that the token was saved with is back
- the run report on the settings page: its heading, only the counts that are not 0, the errors first with translated badges, a filter for each kind, the link to the folder in Files for the target user, and *Copy report*, in English and German
- accessibility of the administration settings and the run report, see [Accessibility](#accessibility)

Optional environment variables:

- `E2E_PORT`: host port for Nextcloud, default `18083`
- `DOCKER_BIN`: Docker CLI path, default `docker`
- `E2E_PROJECT_NAME`: Compose project name, default `paperless_sync_e2e`
- `NEXTCLOUD_IMAGE`: pinned Nextcloud image override
- `E2E_DATABASE`: the database of Nextcloud, `sqlite` by default, `mysql` for MariaDB or `pgsql` for PostgreSQL, see [Databases and object storage](#databases-and-object-storage)
- `E2E_OBJECTSTORE`: the primary storage of Nextcloud, `local` by default, or `s3` for an object store
- `E2E_ACCESSIBILITY=0`: leave out the accessibility check at the end
- `E2E_UPGRADE=1`: run [the upgrade from the last release](#the-upgrade-from-the-last-release) instead of the scenario, with the packages in `E2E_RELEASE_PACKAGE` and `E2E_PACKAGE`, which `packages.sh` downloads and builds when they are empty; `E2E_RELEASE_REPOSITORY`, by default `Dennis-Otto/paperless-sync`, names the repository of the release
- `KEEP_E2E=1`: keep containers and the disposable volume after the suite
- `E2E_IGNORE_MAX_VERSION=1`: enable the app with `--force` on a Nextcloud newer than `max-version`, as `canary.sh` does

All credentials, users, filenames, document content, and metadata are synthetic. The Paperless mock rejects every token except the explicit `e2e-only-token` fixture, an account that is no superuser, with every permission of a run, and the owner of every document; `e2e-view-only-token`, an account without the permissions for the tags, for adding documents and for their tasks; `e2e-no-ui-settings-token`, an account without **View** for UI Settings; and `e2e-superuser-only-token`, a superuser, which alone may list, create and change users and gives the accounts that it created their tokens, `e2e-token-of-<username>`, for their passwords. It records whether uploads arrived intact. Like Paperless-ngx, it answers each endpoint only with its permission, names the ID and the permissions of the account in `/api/ui_settings/`, and filters the documents by their owner. Like Paperless, it refuses an upload without a `Content-Length` with `No file was submitted.` It plays Paperless-ngx 3.3.0, or 2.20.15 and 2.15.3 after `/control/paperless/<version>`: it serves the versions of the API that each of them serves, by the header `Accept` or its default, refuses the others with `406 Not Acceptable`, names itself in `X-Version` and `X-Api-Version`, and lists tasks in the shapes of their serializers. `/control/tasks/<end>` and `/control/task-of/<file>/<end>` end tasks with `success`, `failure`, `duplicate` or `revoked`, as Paperless-ngx 3.x stores them. After `/control/uploads/unavailable`, it answers every upload with `503`, as a Paperless behind a proxy whose worker is down, until `/control/uploads/available`.

## Every supported version at once

`run-all.sh` starts `run.sh` for every supported version at the same time, each in a Compose project of its own, `paperless_sync_e2e_<version>`, on the port `18080 + <version>`, such as `18113` for Nextcloud 33. Besides, it runs the newest version on PostgreSQL, and on MariaDB with an S3 object store, in the projects `paperless_sync_e2e_<version>_pgsql` and `paperless_sync_e2e_<version>_mysql_s3`, on ports 100 and 200 higher, and the [upgrade from the last release](#the-upgrade-from-the-last-release) on PostgreSQL and MariaDB, in `paperless_sync_e2e_<version>_pgsql_upgrade` and `paperless_sync_e2e_<version>_mysql_upgrade`, on ports 300 and 400 higher. While one downloads its images, another one installs, so that all take little longer than one. Each `run.sh` of a version also downloads the image of Playwright in the background while Nextcloud installs, and the accessibility check at the end waits for it; the variants of a database or a storage leave that check out, as it doesn't depend on them. When all are done, `run-all.sh` prints the log of each, in a group of its own in the CI, with a table of the results, the database, the storage, the app, the commit or the upgrade from the last release, and the Nextcloud release that each ran, and fails if one of them failed.

- `E2E_VERSIONS`: the major versions to run instead, such as `"33 35"`; `none` runs only the variants, on `max-version`
- `E2E_VARIANTS`: the variants to run besides, on the newest of the versions, by default `"pgsql mysql+s3 pgsql+upgrade mysql+upgrade"`: each a database, `sqlite`, `mysql` or `pgsql`, with `+s3` for an object store and `+upgrade` for the upgrade from the last release, which runs on the newest version that the release supports as well; `none` runs none
- `E2E_VERSION_TIMEOUT`: the time after which a run that hangs ends as failed, default `15m`, below the 20 minutes of the job in the CI, so that the logs of all runs are still printed

Ctrl-C ends every run, each with the cleanup of `run.sh`, and prints the logs so far. A failed run names the command that runs it again on its own.

`KEEP_E2E=1` keeps the containers of every run. In the CI, the suite leaves its containers running, as the runner is thrown away with them. The suite turns off the password policy's look-up of new passwords at Have I Been Pwned: a request to the internet that the tests don't need and that can fail.

## In the CI

The workflow `.github/workflows/e2e.yml` runs `run-all.sh` in two jobs side by side, each on a runner of its own, and both are required checks of pull requests. `nextcloud` runs every supported version (`E2E_VARIANTS=none`). *nextcloud on PostgreSQL, MariaDB and S3* runs the newest version on [the other databases and S3](#databases-and-object-storage), and [the upgrade from the last release](#the-upgrade-from-the-last-release) on PostgreSQL and MariaDB (`E2E_VERSIONS=none`). In one job, the five installations took more than five minutes on the four cores of a runner; split, the variants finish before the versions, so that a pull request waits no longer than for the versions alone ([decision 0007](../../docs/decisions/0007-end-to-end-tests-on-real-databases-and-storage.md)).

In a pull request, `affected.sh` first compares the merge commit with its base. Only a change of the code, the metadata or the assets of the app (`lib/`, `appinfo/`, `templates/`, `js/`, `css/`, `l10n/`, `img/`, `composer.json`), of the end-to-end tests other than their Markdown and the [contract tests](#contract-tests-against-a-real-paperless-ngx), or of the workflow itself can make the tests fail. In `appinfo/info.xml`, a change that only writes other versions into its lines, as the release bot does in `<version>` and in the addresses of the screenshots and their thumbnails, doesn't count, so a release pull request passes at once, while the upstream bot's change of `max-version`, or a line added or removed, runs the tests. Any other pull request passes the check in seconds, and its summary says *E2E skipped: the change cannot affect the app*.

Of the changes that run the tests, those that can behave differently on another database or storage also run [PostgreSQL, and MariaDB with S3](#databases-and-object-storage): the migrations (`lib/Migration/`), the queries of the state (`lib/Service/SyncStateRepository*`), the files in Nextcloud (`lib/Service/NextcloudStorage*`), the uploads to Paperless (`lib/Service/PaperlessApiService.php`), `appinfo/info.xml` as above, the end-to-end tests and their workflow. The upgrade from the last release runs for a change that can break it: the migrations, the settings and the state that a release stored (`lib/Service/ConfigService.php`, `lib/Model/SyncConfig.php`, `lib/Service/SyncStateRepository*`), the secret of the webhook (`lib/Service/WebhookService.php`), what goes into the package (`.nextcloudignore`, `krankerl.toml`, `scripts/check-package.sh`), `appinfo/info.xml` as above, and the end-to-end tests other than the checks in the browser and their workflow; a change of the package alone runs only the upgrade. For any other change of the app, that job passes at once, and its summary says *E2E on SQLite with local storage only*. `scripts/check-project.sh` tests these rules with sample paths and changes.

Every push to `main`, a run by hand and every night run both jobs in any case: the images `nextcloud:<version>-apache` move with each point release of Nextcloud, which the nightly run catches before the next pull request. A newer push to a pull request or to `main` cancels the run of the older one; a run by hand and the scheduled runs go to the end.

A job that fails explains itself, as every check does: its summary and, after the checks, the comment of the PR coach on the pull request say what failed, why that matters and how to run it on your machine, from [`.github/checks.project.toml`](../../.github/checks.project.toml), also on a pull request from a fork. The table of the summary names each version, database and storage with its result, and the last lines of the log the command that runs one that failed again on its own.

## Databases and object storage

Few installations of Nextcloud run on SQLite: most keep their tables in MariaDB, MySQL or PostgreSQL, and larger ones keep their files in an object store with the API of S3. The state of the app lives in two tables of its own, which its migrations create, and on an object store Nextcloud reads every file as a stream of no known size, which once made Paperless refuse every upload of the inbox ([#73](https://github.com/Dennis-Otto/paperless-sync/issues/73)). `run.sh` runs the same scenario on them as well:

```bash
E2E_DATABASE=pgsql bash tests/e2e/run.sh
E2E_DATABASE=mysql E2E_OBJECTSTORE=s3 bash tests/e2e/run.sh
```

`compose.pgsql.yaml` (PostgreSQL 17), `compose.mysql.yaml` (MariaDB 11.4, with the settings that Nextcloud asks for) and `compose.s3.yaml` join `compose.yaml`. The databases keep their data in memory, for speed. [SeaweedFS](https://github.com/seaweedfs/seaweedfs) serves the API of S3 and accepts only the key of the tests; Nextcloud creates its bucket and keeps every file there, through the variables `OBJECTSTORE_S3_*` of its image. `run.sh` installs Nextcloud on that database and fails if Nextcloud then runs on another database or storage, so that a variant can't pass on SQLite and its disk by mistake. Renovate keeps their images current, each pinned by its digest.

## The upgrade from the last release

Every other run enables the checkout on empty tables, so a migration there never meets a row, and neither does one that moves the data of an installation in use in its `postSchemaChange`, such as the binding of the token to its URL, the lazy settings or the German names of the folders of an installation in use. Every user of the app runs the migrations on the rows of their installation, when they update the app from the App Store, and one that fails there leaves Nextcloud in maintenance mode or disables the app on every server at once. Nor did a run install the package that users get: the signed one of a release, or the one that krankerl builds from the commit with `.nextcloudignore`. `upgrade.sh` does both, on PostgreSQL and on MariaDB, where most installations keep their tables ([decision 0028](../../docs/decisions/0028-test-the-upgrade-users-run.md)):

```bash
E2E_DATABASE=pgsql E2E_UPGRADE=1 bash tests/e2e/run.sh
E2E_VERSIONS=none E2E_VARIANTS="pgsql+upgrade mysql+upgrade" bash tests/e2e/run-all.sh
```

  <img src="../../docs/images/diagrams/how-the-upgrade-test-runs.svg" alt="How the upgrade test runs: The upgrade test installs the signed package of the last release, which occ integrity:check-app must find intact while a copy with one changed file fails, and uses it as an administrator does, with the token, per-user ownership, the webhook, the copies of two owners, an import, a retry and a file to send. It records every row, setting, credential, migration and file ID. Then the package of the commit, which krankerl builds as the release does, replaces the release, and occ upgrade runs every new migration on those rows. 1. `packages.sh` downloads `paperless_sync.tar.gz` of the latest release on GitHub into a file, never into a pipe, and builds the package of the commit with krankerl, as the release workflow does, or, without krankerl, from the runtime files of `HEAD` that `scripts/check-package.sh` names, the same files. Both take the commit, not the working tree: commit a change before the upgrade can see it. `compose.upgrade.yaml` keeps the checkout out of the folder of the app, and the test unpacks each package into the volume of Nextcloud, as an update does.
2. `occ integrity:check-app` must find the release intact and signed; a copy of it with one changed file must fail the same check, so that its pass proves something.
3. The release is used as an administrator uses it: the token, per-user ownership with a user of Paperless mapped to another user of Nextcloud, the secret of the webhook, and runs of `occ paperless_sync:run` until the tables hold the copies of two owners, an import whose task Paperless hasn't finished, an import that waits to be tried again after Paperless refused its upload with `503`, and a file that waits to be sent from Files. `upgrade_state.php` records every row of every table of the app, its configuration, its credentials, its executed migrations and every file below the base folder of each user with its ID, and the settings page its settings and the state of the webhook.
4. The package of the commit replaces the release. While the commit still has the version of the release, as between two releases, the test gives it the next patch version, as the release bot will: Nextcloud runs the migrations of an app only for a newer version. `occ upgrade` must pass, Nextcloud must leave maintenance mode, `occ app:list` must show that version, and the table `migrations` must hold exactly the migrations of `lib/Migration/` of the package.
5. `assert_upgrade.py` then compares: every row, column, value, credential, migration and file ID of the release must be there with its value, while new columns, tables, values and settings may come; only `installed_version` and `types`, which Nextcloud writes with every update, may change, and what a migration of the commit changes on purpose, which it names in `UPGRADE_CHANGES` of `upgrade.sh`, as `TABLE.COLUMN` or `appconfig.KEY`, with its reason. The next run must reach Paperless with the stored token, download and upload nothing and leave the retry waiting until the same time; the import of the release must end once Paperless finished its task, and the webhook must accept its secret.

The steps against the release speak only what administrators and their scripts use: the settings, `occ paperless_sync:run`, WebDAV and the routes of *Send to Paperless* and of the webhook. A change of one of them must keep its old way working in `upgrade.sh` until the next release, which the test then starts from. A test-only migration that adds a column `NOT NULL` without a default to a table with rows turns the upgrade red on PostgreSQL, while every other run passes; `test_assert_upgrade.py`, which `scripts/check-project.sh` runs, checks that `assert_upgrade.py` finds each loss it looks for. The upgrade runs on the newest version of Nextcloud that both the release and the commit support, as the users of the release have it before they update; with no such version, `run-all.sh` says that no installation could update the app without updating Nextcloud first.

At the end of the scenario, `accessibility.mjs` checks the pages of the app in Chromium with [axe-core](https://github.com/dequelabs/axe-core) against WCAG 2.1 at levels A and AA, in the light and the dark theme of Nextcloud, each in a window of a computer, 1280 CSS pixels wide, and of a phone, 320 pixels wide, which the page switches to without loading again. ## Screenshots

The pictures of the documentation in `docs/images/` and of the App Store in `screenshots/` come from the same containers, and so do those of the German documentation in `docs/images/de/`, which `README.de.md` and the German pages of the website show:

```bash
bash tests/e2e/screenshots.sh        # English and German
bash tests/e2e/screenshots.sh de     # German only
```

Each language gets an installation of its own, whose `default_language` and `default_locale` are `en` and `en_US`, or `de` and `de_DE`, so that Nextcloud, the app and the folders that a new installation proposes, `Dokumente/Paperless`, `Archiv` and `Eingang` in German, speak it. `language.mjs` holds what the pictures of each language look for: the texts of the app come from its catalog `l10n/de.json`, a text of Nextcloud itself, such as *Folder tree*, from a small table, and the files of the story, such as the receipt in the inbox, have names in that language; the documents of Paperless stay the English ones of `showcase.py`. The German pass writes no screenshots of the App Store, which shows them in English. `scripts/check-project.sh` runs `node --test language.test.mjs`, which fails when a text that `screenshots.mjs` looks for with `L.t(…)` has no German in the catalog.

The Paperless mock serves a small household archive of invented documents (`showcase.py`): fourteen documents of seven correspondents, one still in the Paperless inbox, each a one-page PDF. `screenshots.mjs` then follows the quick start in Chromium: a dry-run and the first synchronization, recorded as `dry-run.gif`; the settings, each of their sections, the preview under the path template with a new template, and the archive in Files, in the light and the dark theme; a walk through the archive to a document in the viewer, recorded as `archive.gif`; and a dry-run a few days later, when the archive has a new title, a document in the trash, one with the excluded tag *Private*, two new documents and a finished import.

Each screenshot of the App Store gets a small thumbnail next to it, `screenshots/<name>-small.png`, which the list of the apps in the App Store shows: `thumbnail.mjs` shrinks it to fit 640 × 400 pixels, twice the 200 pixels of height that the list gives it, each pixel the average of those it covers, and `scripts/check-project.sh` tests it with `node --test thumbnail.test.mjs`. `appinfo/info.xml` names both pictures of each screenshot at the tag of the release, and `tests/Unit/AppInfo/ScreenshotsTest.php` checks that each thumbnail is there, with the size of its screenshot shrunk into that box.

The GIFs show a drawn pointer, since a screenshot has none, and share one palette across their frames. The image of Playwright has no font for the interface of Nextcloud, so the script installs Inter (`fonts.conf`). `E2E_PORT` (default `18084`), `E2E_PROJECT_NAME` and `KEEP_E2E=1` work as for `run.sh`. Look at every picture before committing it.

### The same pixels on every run

Two runs of the script draw the same pixels, so that a picture changes only when the app looks different. The data of the mock is fixed, and `frozen.mjs` freezes everything else that the server writes anew on each run, in the answers that the browser gets and never in what the server keeps: each moment of a run shows the moment of the story at which the browser first saw it, 10:20 for the first dry-run, 10:21 for the first synchronization and 10:22 for the runs a few days later, the new secret of the webhook shows as an example secret, and every file in Files changed "a few seconds ago". Every picture, and every frame of an animation, waits until the page stands still: no part of it scrolling any more, such as to a new report, its images decoded, its transitions at their end, and two pictures in a row the same; and Chromium decodes each image as it draws it and draws each tile whole (`--disable-checker-imaging`, `--disable-partial-raster`), without which it drew the avatar in the header in one of two ways from run to run. An animation takes its frames at fixed steps of what it shows: it waits for the server without frames, and draws a scroll of the page, such as the one to a new report, in eight fixed steps. `scripts/check-project.sh` tests the frozen clock with `node --test frozen.test.mjs`.

## The coming Nextcloud

Every Monday, and when started by hand, the workflow also runs the suite against the coming Nextcloud:

```bash
bash tests/e2e/canary.sh
```

The coming Nextcloud is the newest beta or release candidate of the next major version while Nextcloud publishes one, in `https://download.nextcloud.com/server/prereleases/`, and otherwise the daily build of its master branch, `https://download.nextcloud.com/server/daily/latest-master.tar.bz2`. Nextcloud no longer publishes Docker images of betas and release candidates, so the script checks the signature of the package against the release key of Nextcloud, as the official image does, and puts its code into the image of the newest release, `nextcloud:apache`, which keeps its PHP, Apache and start script. The suite enables the app with `--force`, as `max-version` of `appinfo/info.xml` doesn't name that version yet; the upstream bot raises `max-version` once Nextcloud releases the version.

The canary is no required check and blocks nothing. When it fails, it opens the issue *The coming Nextcloud breaks the app* with a link to the run, adds every further failed run to it, and closes it once the tests pass again.

A failure of the canary is either a change of Nextcloud that breaks the app or one that breaks only a test. `KEEP_E2E=1 bash tests/e2e/canary.sh` keeps the coming Nextcloud running at `E2E_PORT` after the failure, so a script of Playwright in the network of the Compose project, as `run.sh` starts it, can look at the page as the test saw it: its errors in the console, its address and what it shows.

Optional environment variables, besides those of `run.sh`:

- `CANARY_BASE_IMAGE`: the image whose code the coming Nextcloud replaces, default `nextcloud:apache`
- `CANARY_IMAGE`: the local image the script builds, default `paperless-sync-e2e:coming`

## Contract tests against a real Paperless-ngx

The mock answers as the app expects Paperless to answer, and so do the answers in the unit tests; twice, both had drifted from Paperless, in the checksums of Paperless-ngx 2.x and in the tasks of 3.x. The contract tests start a real Paperless-ngx instead, the last release of 2.x (2.20) or the current release of 3.x, and check what it answers:

```bash
bash tests/e2e/run-contract.sh 2
bash tests/e2e/run-contract.sh 3
```

  <source media="(prefers-color-scheme: dark)" srcset="../../docs/images/diagrams/what-the-contract-tests-check-against-a-real-paperless.dark.svg">
  <img src="../../docs/images/diagrams/what-the-contract-tests-check-against-a-real-paperless.svg" alt="What the contract tests check against a real Paperless: run-contract.sh starts a real Paperless-ngx, the last release of 2.x or the current release of 3.x, next to Nextcloud. contract.py seeds Paperless through its REST API and checks every answer that the app reads, then the app runs its export, a move, the trash and the inbox against it. `compose.paperless.yaml` adds Paperless and Redis to `compose.yaml`, by the profile `paperless-2` or `paperless-3`, each line in a Compose project and on a port of its own, so that both run side by side. Renovate keeps both images current by their digests, 2.x within 2.x. Paperless reads the text of the PDFs of the tests without OCR and still keeps an archived version of each, as with scanned documents.

`contract.py` runs in the container of the mock, with Python alone, and does what a household does in Paperless, through its REST API with the token of a synthetic administrator: it uploads three PDFs, waits for their tasks, sets their titles, correspondents, document types, a storage path and a custom field of the type select, writes a note on one, puts one into the trash and back, and uploads a PDF that Paperless can't read, the same file twice and a file of a type that it doesn't take. It checks each answer that the app reads, with every request as the app sends it:

- the documents of a run, which carry the fields of `PaperlessApiService::DOCUMENT_FIELDS` and no other, in pages that follow each other, and with their notes and the names of their authors, as a run asks for them while it writes the metadata next to the archive;
- the trash with `deleted_at`, and the lists of tags with the inbox tag, correspondents, document types, storage paths, custom fields with the IDs of their choices, users, and the account with its permissions;
- the tasks of the uploads, in version 9 and, on 3.x, in version 10 of the API: the document of a success, the reason of a failure, a duplicate, which 2.x refuses and 3.x consumes by default, and a task that Paperless doesn't know;
- the checksums of the metadata, which are the MD5 (2.x) or the SHA-256 (3.x) of the original and the archived download ([decision 0009](../../docs/decisions/0009-checksums-of-paperless-2-and-3.md)), and the search for a document by the checksum of its file;
- the versions of the API: 9 on both lines, 10 on 3.x only, 99 refused with HTTP 406;
- the requests of the setup of the account of the app: the filter of a username, which compares without case, a new user that is no superuser with its permissions by their codenames, a second one of the same name, which Paperless refuses, an update with a new password and other permissions, and the token of the user, which stays the one that it had.

Then the app runs against that Paperless in Nextcloud, and at the end sets up its own account with the token of the administrator, whose checklist fails nowhere; the commands for `curl` between the markers `account-snippet` of `README.md` create another account in the container of Nextcloud, whose token passes the checklist too: it exports two documents with the bytes of their archived versions and writes the sidecar of the invoice, with its note, its author and the label of its custom field, moves one to its new title, keeping the ID of its file, follows it into the trash of Paperless and back, and sends a PDF and a broken file from its inbox, which ends as a new document and in the error folder with the reason of Paperless. The status names the version of Paperless, and the log of Nextcloud has no error of the app and never its token.

The answers of Paperless are the fixtures of the unit tests, in `tests/fixtures/paperless-ngx-2/` and `tests/fixtures/paperless-ngx-3/`, which `PaperlessApiServiceTest` reads. Each run compares the shapes of the new answers with them: a field that Paperless added is a note, a field or an answer that is gone, or a field of another type, fails the run. When the app reads the new answers correctly, record them anew and commit them:

```bash
CONTRACT_RECORD=1 bash tests/e2e/run-contract.sh 3
```

In the CI, the jobs *Paperless-ngx 2.x* and *Paperless-ngx 3.x* of `.github/workflows/e2e.yml` run every Monday with the canary, when started by hand, and in a pull request that changes how the app talks to Paperless: its client (`lib/Service/Paperless*`, `lib/Model/DocumentFingerprint.php`), the mock, the fixtures, the contract tests or the workflow (`affected.sh` with `E2E_QUESTION=contract`). Each keeps the answers of Paperless as an artifact of the run, so new fixtures need no Docker. They are no required checks ([decision 0015](../../docs/decisions/0015-check-the-mock-against-a-real-paperless.md)); when they fail on Monday, they open the issue *The contract tests against Paperless-ngx fail*, add every further failed run to it, and close it once they pass again. The contract tests also read the paths, reports, settings and status of the app, so a change there can fail them too; the log of the run says which answer differed.

On Paperless-ngx 2.x, a task that has just failed first reports `<traceback object at 0x…>` as its result and its reason a moment later; the contract tests wait for the reason, as the app does ([issue #161](https://github.com/Dennis-Otto/paperless-sync/issues/161)).

Optional environment variables:

- `CONTRACT_RECORD=1`: write the answers of Paperless into the fixtures instead of comparing them
- `CONTRACT_RECORDINGS`: a folder that keeps the answers of the run
- `E2E_PORT`, `E2E_PROJECT_NAME`, `KEEP_E2E=1`: as for `run.sh`; the port defaults to 18092 for 2.x and 18093 for 3.x
