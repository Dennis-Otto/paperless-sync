# Architecture

[← README](https://github.com/Dennis-Otto/paperless-sync) · [Security design](security.md) · [Roadmap](roadmap.md) · [Releases](releases.md)

Paperless Sync is a Nextcloud app in PHP. It runs inside Nextcloud, reads Paperless-ngx through its REST API and writes files through Nextcloud's file API. It has no server, daemon or port of its own.

## Data flow

One run, from the background job to the status:

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="images/diagrams/one-run-of-the-synchronization.dark.svg">
  <img src="images/diagrams/one-run-of-the-synchronization.svg" alt="One run of the synchronization: A background job, the settings page with a dry run, or an occ command starts a run. Paperless Sync takes the lock, checks the configuration, and tests the connection to Paperless-ngx and the base folder in Nextcloud. Inbox: it asks Paperless for the tasks of earlier uploads, removes imported files from Nextcloud and moves failed ones, uploads new, changed and due files to Paperless, and stores their tasks, refusals and retries in the database. Export: it reads every page of the documents, the trash and the metadata from Paperless, checks that every list came back complete, compares their paths and checksums with those in the database, downloads new and changed documents, writes, moves, trashes and deletes their files, and saves paths, checksums and missing runs. Finally it prunes empty folders, records the status and releases the lock.">
</picture>

1. Nextcloud's cron starts the background job every five minutes. It runs only when synchronization is enabled and the configured interval has passed since the last run that synchronized; a dry-run counts only while it is still running. An administrator can start a dry run on the settings page, which runs in the request, and a run, which the page queues as a background job of its own, `ManualSyncJob`, that the next background jobs start; the page follows it through the status. `occ paperless_sync:run` starts a run or a dry run in the shell, with the batch size of the settings, another or none ([decision 0018](decisions/0018-runs-by-hand-in-background-jobs.md)).
2. The run takes a lock, reads its settings and its connection to Paperless together, with one decryption of the API token, checks that the app is configured, and tests the connection to Paperless and the base folder in Nextcloud. It keeps that connection to its end: settings saved during the run reach the next run, as the picture below the steps shows.
3. **Inbox:** the files of the inbox folder are uploaded to Paperless, at most as many as the batch size allows. Each file goes up from a copy in Nextcloud's temporary folder, so that the request has a `Content-Length` also when the file lies on object storage, with the tags of its subfolders and those for every import, which the run looks up once among the tags of Paperless and creates when it may (`lib/Service/InboxTags.php`). Their tasks are followed in the next runs: after success the file is deleted or kept, as configured, and the report names the new document; after a failure, a duplicate or a task that Paperless revoked, it moves to the error folder, next to a text file with the reason and the ID of the task. A task that Paperless has not finished a day after the upload ends by the content of the file: a document with its checksum in Paperless is a success; a task that Paperless still lists, unfinished, moves the file to the error folder, because Paperless-ngx 3.x would import a second upload as a duplicate; a task that Paperless doesn't list sends the file to the wait of a failed upload, after which it goes up again. A file that Paperless refuses at once, with `400`, `413`, `415` or `422`, is remembered with its ETag and skipped until it changes. Any other failure, such as a timeout or a `5xx`, ends the uploads of the run, and the file waits for its next attempt: 15 minutes, doubled after each failure, at most a day.
4. **Export:** every document gets its path from the path template. A new document is downloaded to a temporary file, which goes on to Nextcloud as it is, in chunks; one pass over it computes its SHA-256 and MD5 checksums, so that no document is in memory as a whole. A document with a new revision in Paperless is compared by the checksum that Paperless reports, MD5 up to Paperless-ngx 2.x and SHA-256 since 3.0: when it is one of the saved two, a document whose metadata changed moves to its new path; otherwise the document is downloaded, and its file moves to its new path, if it has one, and gets the new content in place. A copy at the path of a document with its content stays as it is, also when the document comes back from the Paperless trash or after it was missing. A file that an earlier version exported has only its SHA-256 saved; when Paperless reports an MD5, one read of the mirrored file adds it, as long as the file still has that SHA-256. Documents in the Paperless inbox and documents with an excluded tag are skipped, and their mirrored copies removed. Every change takes its place in the batch, also one that fails, and failed exports take their places only among the exports. The most recently added documents come first, documents whose last change failed after the others. Before every write, the app checks the free space, because Nextcloud applies no quota to the temporary file of a write; a full quota, an archive that is no longer writable or an unavailable storage ends the exports and moves of the run at its first failure.
5. **Trash and deletion:** a document in the Paperless trash moves to the deleted folder. A document that is missing from both the API and the trash for the configured number of complete runs in a row moves to the deleted folder too, and is deleted only when permanent and direct deletion are enabled. A scan is complete when every page came back full, with the same count of Paperless, and the run received every document that Paperless listed, read in the order of their IDs; after an incomplete scan, no document counts as missing. Before a complete scan counts a document as missing, the run asks Paperless for that document alone, because pages that shift while the run reads them can leave out one that still exists: only `404` counts, a document that Paperless still has starts its count anew, and an error counts nothing for its document in this run.
6. Empty folders are pruned, the state is saved, and the status records the report. The Activity stream of the target user gets an entry for the changes of the run and one for each import result, also when the run failed after its first changes. A run that failed or completed with errors counts towards the notification of the administrators, and a failed or refused import notifies the target user. A dry run does all of this without writing anything, and adds no entry and no notification.

### A dry-run takes the plan of a run

A dry-run and a run take one way through the steps 3 to 5: the planners decide what happens to each document and each file of the inbox, and only the executors tell the two apart ([decision 0022](decisions/0022-a-dry-run-takes-the-plan-of-a-run.md)).

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="images/diagrams/how-a-dry-run-and-a-run-share-one-plan.dark.svg">
  <img src="images/diagrams/how-a-dry-run-and-a-run-share-one-plan.svg" alt="How a dry-run and a run share one plan: The planners read the documents, the trash and the tasks of Paperless, the inbox and the archive in Nextcloud, and the states in the database, and change none of them. They plan one action at a time for each document and file, such as an export, a move, a move to the deleted folder, a deletion or an upload, when it fits the batch, and leave it for a later run otherwise. In a run, the executor makes the change and saves the state; in a dry-run, it changes nothing. Both report the same line and take the same place in the batch, so the plan of the next document sees the batch as it stands: in a run, a failed export frees its place, and a full quota stops the other writes.">
</picture>

- **`ExportPlanner`** plans the export: for each active document whether its copy stays, waits for a later run, or is exported or moved, with the conflicts that stop it; for each document in the trash and each one that Paperless no longer lists whether its copy moves to the deleted folder, is deleted or waits for its missing scans, after it has asked Paperless for each document that a scan would count as missing. When the batch is full, a document with a new path waits without a question to Paperless or a read of its copy; one that keeps its path is still asked once for the checksum of its revision, which its state keeps for a later run.
- **`ImportPlanner`** plans the inbox: how the uploads of earlier runs ended, by their tasks in Paperless, which files go to Paperless next, and which stay aside for their type, by `InboxFileTypes`.
- **`ExportExecutor`** and **`ImportExecutor`** apply each action: a run writes, moves and deletes the files, uploads them and saves the states; a dry-run reports the same lines and changes nothing. An error concerns only its document or file, and the state keeps it, so that the log has it once.
- **`SyncBatch`** holds the places of the changes. The plan is lazy: it plans each document once the executor has applied the one before, so a failed export leaves its place to the next document, and after a full quota the other exports and moves wait for the next run. A dry-run counts each change as if it succeeded, so it shows the batch of a run in which nothing fails.

A new kind of change is a new action of a planner, which its executor applies, or reports in a dry-run; a planner never asks which kind of run it plans. A test runs a dry-run and the run after it for each kind of change and compares their reports.

## Tests

Three kinds of tests check the app: unit tests, which `scripts/check.sh` runs before every push, end-to-end tests in Docker, and mutation tests, which check the unit tests themselves.

<picture>
  <source media="(prefers-color-scheme: dark)" srcset="images/diagrams/the-synchronization-in-the-unit-tests.dark.svg">
  <img src="images/diagrams/the-synchronization-in-the-unit-tests.svg" alt="The synchronization in the unit tests: A unit test sets up Paperless-ngx, the files of Nextcloud, the state, the configuration and the clock in memory, and runs the synchronization of the app through the interfaces it uses in Nextcloud. Then the test checks the report, the files of every user, the state of every owner, the status and the record of every call.">
</picture>

- **Unit tests** in `tests/Unit` run every line of `lib/`; `scripts/check.sh` fails when one runs in no test. The synchronization runs as in Nextcloud, against doubles in memory behind the same interfaces. The doubles are strict, so that a test sees what a mistake of the app would do: the files keep each user apart and record every call with its user, the state keeps each owner apart, Paperless serves an original that differs from the archived version and records every download, every connection that a run takes and every test of it, and Nextcloud's clock stands still until a test sets or advances it, so that no test depends on the time it runs at.
- **End-to-end tests** in `tests/e2e` run the app in every supported version of Nextcloud, in Docker, against a mock of Paperless-ngx ([decision 0005](decisions/0005-end-to-end-tests-where-they-can-fail.md)).
- **Mutation tests** change the code of `lib/` in more than six thousand small ways with [Infection](https://infection.github.io/) and run the unit tests against each change, a mutant. A mutant that no test notices shows a line that the tests run but don't check. The workflow *Mutation* runs them every week, with the configuration of `infection.json5` in the root of the repository, and reports the score, the MSI: the share of the mutants that the tests noticed.

## Design decisions

- **Paperless is the source of truth.** Nextcloud gets a mirror; the app sends no change of the mirrored files back to Paperless.
- **The marker `[P<ID>]`** in every file name ties a file to its document, so a renamed document is found again, and [Paperless Unified Search](https://github.com/Dennis-Otto/paperless-unified-search) can open it. The app adds it to a template that leaves it out, and it shortens only the free text of a name that would be too long, never the marker. A file of the inbox is named by whoever may write there, so it loses every marker on its way to the error folder, where it could otherwise pass for the copy of a document.
- **No WebDAV and no password of Nextcloud.** The app writes through Nextcloud's file API in the name of the target user.
- **Mirrored files keep their identity.** Nextcloud ties shares, public links, comments, tags, favorites and versions to the ID of a file, so the copy of a document stays the same file: a change of the metadata moves it, and a change of the content writes it in place with `File::putContent()`, under Nextcloud's exclusive lock. The versions app keeps the previous content as a version in every run: it looks for the file among the files of the user who is logged in, and a run never runs in the request of a user, since *Synchronize now* queues a background job ([decision 0018](decisions/0018-runs-by-hand-in-background-jobs.md)). Only a new file is written to a temporary `.part` file first and moved into place. The trade-off: on local storage, a write in place that fails halfway, such as on a disk that runs full, leaves the file incomplete until the next run writes it again; the document is complete in a temporary file of the server by then, so the window is as short as a local copy. With the conflict policy *Skip and report conflict*, the app's own copy is no conflict: the state records its path, and the file still has the content of the last download, or the state marks it as being written, so that a copy that a failed write left incomplete is written again. A copy that someone changed stays, also when its document moves to a new path ([decision 0010](decisions/0010-mirrored-files-keep-their-identity.md)).
- **Both checksums of every download.** The database keeps the SHA-256 and the MD5 of every file, so that the checksums of Paperless-ngx 2 and 3 both tell a change of the metadata, which moves the file, from a change of the content ([decision 0009](decisions/0009-checksums-of-paperless-2-and-3.md)).
- **One connection for each run.** A run reads its settings and the API token once, at its start, and reaches Paperless through a client of that connection alone, so a save during the run never mixes two Paperless in one run and the token is decrypted once, not with every request ([decision 0020](decisions/0020-one-connection-to-paperless-for-each-run.md)).
- **Bounded and resumable runs.** The batch size limits the changes of one run, failed ones included, and the state lets the next run continue where it stopped.
- **A dry-run takes the plan of a run.** The planners decide what happens to each document and file and change nothing, and the executors apply each action or, in a dry-run, only report it, so a dry-run shows the changes of the run that follows it ([decision 0022](decisions/0022-a-dry-run-takes-the-plan-of-a-run.md)).
- **A run costs what changed.** A run asks Paperless for the documents with only the fields that it reads, listed in `PaperlessApiService::DOCUMENT_FIELDS`, so their text, notes and permissions stay in Paperless; a test fails when the code reads a field of a document that the list leaves out, such as a new variable of the path template. It asks for the checksum of a document once for each revision: when the batch is full, a document with a new path waits without the request, and the state keeps the checksum with its revision for one that waits at its path or whose change fails. The run reads the state of every export once, at its start, and writes a state only when one of its values changes, so a run over an archive without changes writes nothing to the database. The settings and the status are lazy keys of the app configuration, which Nextcloud loads when the app asks for them, not with every request of every user.
- **Only Paperless confirms a deletion.** A page that came back short or empty, or a list that changed while the run read it, makes no document count as missing, and a complete scan counts a document as missing only after Paperless has answered `404` for it alone ([decision 0004](decisions/0004-delete-only-what-is-confirmed.md)).
- **Safe by default.** Synchronization is off until a configuration works, and permanent deletion is off until an administrator turns it on.
